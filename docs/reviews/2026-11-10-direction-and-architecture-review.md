## 1. 总体结论

**项目方向没有根本性走偏，核心能力也不是“尚未做出来”。当前主要问题是：私人实例中长期积累的附加能力被较完整地迁入公共上游，使首个版本的体量、依赖和验证范围偏大，而最初定义的部分行为验收与实际发布闭环尚未完成。**

具体判断如下：

1. **产品方向基本一致。** Markdown 事实源、独立 CLI、单一伞形 Hermes 技能、公共源码与私人实例分离，均符合 `IDEA.md`。
2. **实现不能笼统称为过度冗杂。** 去重、原子写入、原始快照、本地媒体、失败可见、状态恢复和候选闭环都是实际领域需求。
3. **首版范围与可选能力占比偏重。** 加密 Pages、双通道投递、站点专用适配器及其测试占据了较大比例，可选能力与核心能力的成熟度尚未充分区分。
4. **当前更像“功能迁移基本完成，发布与验收尚未收口”。** 不需要推倒重做，也不建议为了降低行数而删除可靠性保护或测试。
5. **文档治理应收敛。** 建议保留公开的 `IDEA.md` 作为稳定愿景，另设公开 `ROADMAP.md` 承载版本路线和待验收事项。该建议尚未作为项目变更执行。

- 先读 `README.md`，再以 `IDEA.md` 为最初方向基线。

- 区分以下四种状态：
  - **已实现且有当前测试证据**；

## 3. 与最初建立方向的对照

`IDEA.md:21-30` 提出的六项核心能力都已有实际实现：

| 最初能力 | 当前实现与判断 |

| 本地阅读与可选发布 | 已有较多实现，范围甚至超过首版最小需要 |

### 3.1 没有发生的关键方向偏移

- **CLI 可以脱离 Hermes 使用。** `bin/ca:29-45` 直接调度收藏、完成、索引、检索、审计等脚本。
- **Hermes 不是唯一事实源或自动编辑服务。** 中文标题、摘要和分类由用户或 Agent 提供，工具包负责执行与校验，符合 `IDEA.md:19`。
- **Markdown 仍是内容事实源。** 索引从 `library/` 重建，见 `scripts/rebuild_index.py:94-130`。
- **公共树与私人实例保持分离。** 示例源默认禁用；没有发布配置或 `enabled: false` 时，`scripts/publish_site.py:1684-1692` 跳过发布。
- **仍只有一个伞形技能。** 没有按厂商、分类或渠道拆成多个技能。
- **没有变成数据库应用或托管平台。** GitHub Pages、NAS、消息渠道仍是可选外部目标。

### 3.2 平台范围收缩不是方向性缺陷

审阅最终基线已明确将支持和 hosted CI 范围限定为 Linux/Ubuntu；历史 macOS 失败没有被改写为通过。该决定记录在 `docs/ci-acceptance.md:50-56`，并与当前 README、部署文档及发布流程一致。

这符合 `IDEA.md:147`“支持平台应遵循实际行为和测试”的原则。它是经过确认的支持范围决定，不应误报为已修复或通过 macOS。

## 4. 实现是否过于冗杂

### 4.1 核心部分的复杂性大体合理

以下机制直接对应 `IDEA.md:70-79` 的可靠性、证据与失败可见原则：

- URL 规范化、内容哈希和并发去重；
- 原始快照、本地媒体及媒体预算；
- SSRF、重定向、文件输入与输出路径边界；
- 原子目录预留、完成、索引与状态写入；
- `seen.json` 损坏恢复和索引一致性审计；
- 采集水位、候选闭环、失败可见及重试队列。

例如，`scripts/fetch_sources.py:31-59` 处理回看窗口、重试证据、并发状态合并和 dry-run；这些属于定时采集的真实需求，而不是无意义的形式主义。

**测试数量本身不是过度设计。** 对会长期修改个人档案的工具，615 项测试所体现的安全与回归投入总体合理。

### 4.2 可选能力在首版中的占比明显偏大

按“本地阅读、加密发布、双通道投递及其直接测试”这一明确分组统计：

| 分组 | 文本行数 | 比例 |
|---|---:|---:|
| 相关 Python 实现 | 4,524 / 12,767 | **35.4%** |
| 相关 Python 测试 | 5,879 / 15,190 | **38.7%** |

该实现比例尚未计入 `scripts/archive_page.html` 和 `scripts/encrypted_reader.js`。

主要模块体量：

- `scripts/publish_site.py`：1,799 行；
- `scripts/deliver_daily.py`：1,289 行；
- `scripts/encrypted_site.py`：916 行；
- `scripts/build_html.py`：520 行，另有 883 行 HTML 模板。

这些数字不证明功能应该删除，但说明首个公共版本承担的不仅是核心归档工具，还继承了原私人实例较完整的发布与投递系统。

`IDEA.md:148` 原本要求消息、NAS 和托管发布适配器在通用安装路径得到验证后，再作为可选能力记录。当前实际是代码和合成测试较多，而通用安装、真实浏览器、真实实例和真实发布验收未同步完成。**这里存在验证顺序和首版范围失衡，而不是产品方向错误。**

### 4.3 公共工具包仍保留原实例的结构痕迹

这些不是隐私泄漏，但会限制通用性：

- `scripts/rebuild_index.py:23` 固定 OpenAI、Anthropic、Kimi、GLM、微信公众号的展示顺序；
- `scripts/rebuild_index.py:70-84` 使用硬编码规则识别厂商；
- `scripts/fetch_sources.py:1035-1041` 注册通用 RSS 加若干站点专用适配器；
- `scripts/deliver_daily.py:1-17` 固定为“邮件全文 + 微信 200 字摘要”；
- `bin/ca:68-73` 将该双通道组合写入公共 CLI 帮助。

因此，当前更接近“已去除私人内容、但仍保留原实例功能组合的公共版本”，而不是“核心很小、厂商与渠道全部通过通用扩展接入的工具包”。后者并非 `IDEA.md` 规定的首版硬性条件，**不建议为此在 v0.1 前进行大规模插件化重写**。

### 4.4 “可选”主要是行为可选，不完全是依赖和运行路径可选

存在一处明确的文档与实现不一致：

- `skills/content-archive/references/deployment.md:43` 表示阅读器和发布依赖应分离，基础收藏不应拉入发布依赖；
- `requirements.txt:19-21` 已包含 `cryptography` 和 `markdown-it-py`；
- `requirements-publish.txt:3-6` 又声明这些依赖；
- `scripts/rebuild_index.py:15,127-128` 在普通 `index` 中始终生成 HTML 阅读器。

当前更准确的描述是：发布行为可选，但阅读器生成不是独立可选步骤，部分可选组件依赖仍包含在基础安装中。这不证明运行时错误，但说明分层尚未完全落实。

### 4.5 可维护性债务存在，但不应优先于验收收尾

主审阅静态核对到：

- `scripts/archive_url.py:803` 的 `main()` 约 549 行；
- `scripts/fetch_sources.py:1444` 的 `main()` 约 398 行；
- `scripts/build_digest.py:127` 的 `main()` 约 280 行；
- 状态锁在 `scripts/common.py:524`、`scripts/fetch_sources.py:149`、`scripts/daily_gate.py:33` 重复实现；
- `daily_gate.py` 与 `deliver_daily.py` 存在互相延迟导入；

- 测试以 `phase*`、`wave*`、`batch*` 命名，保留原项目的修复历史，而不是按公共能力组织。

这些会增加新维护者的理解成本，属于后续维护性问题，**不是当前推倒重构或削弱测试的理由**。

## 6. 文档治理建议：IDEA 与路线图分离

**本节是审阅建议，不是已经批准或执行的文档重构。**

### 6.1 推荐原则

保留并公开 `IDEA.md`，但把它收敛为稳定的“项目宪法”；后续路线图单独放入根目录 `ROADMAP.md`。不建议继续把版本计划、验收进度和待办事项都堆入 `IDEA.md`。

| 文件 | 回答的问题 | 更新频率 |
|---|---|---|
| `IDEA.md` | 为什么存在、要成为什么、坚持哪些原则、明确不做什么 | 很少更新 |
| `ROADMAP.md` | 接下来做什么、各版本目标、未验收能力和待决策事项 | 随阶段更新 |
| `README.md` | 当前实际能做什么、如何安装使用、当前发布状态 | 随能力与版本更新 |
| `CHANGELOG.md` | 已经发生了什么变化 | 每次发布 |
| `docs/acceptance.md` 等 | 某历史阶段实际验证了什么 | 作为证据保留 |
| `docs/releasing.md` | 如何验证和发布候选版本 | 流程变化时更新 |

这样可以分开长期方向、首版迁移工作、验收标准、开放决策和当前状态。

### 6.2 `IDEA.md` 建议保留的内容

- 项目存在的原因与愿景；
- 核心能力的高层定义；
- Markdown 事实源、单一伞形技能、实例规则归属等设计原则；
- 公共上游、私人实例和托管目标的三层边界；
- 固定版本升级原则；
- 非目标。

它应当足够稳定，半年后阅读仍然成立，不需要因为完成一个版本就改写。无需仅为命名习惯改成 `VISION.md`；现有 `IDEA.md` 已被 README 和项目规则引用。

### 6.3 建议迁出或删除的内容

1. **初始迁移方法**：`IDEA.md:118-129` 是一次性工作，且迁移已发生。详细历史由 `docs/acceptance.md` 和迁移基线保存；愿景文档只保留通用的审查、固定版本迁移原则即可。
2. **首版验收标准**：`IDEA.md:131-142` 属于 v0.1，而不是永久愿景。可移入 `ROADMAP.md` 的 v0.1 部分或链接到专门验收记录，并标记已实现已验收、已实现但证据不足、尚未完成及对应证据。
3. **已解决的 Open decisions**：`IDEA.md:144-148` 中 MIT 许可证和 Linux 支持范围均已决定，不再是开放决策；可选适配器的真实安装验收可进入路线图。

### 6.4 `ROADMAP.md` 的建议组织方式

按结果和里程碑组织，不按日期堆砌任务，也不复制完整测试清单。建议首版结构：

- **v0.1.0——完成可复用发布闭环**：既有归档 search/update 验收、技能正反触发验证、最终发布包干净安装与完整冒烟、精确提交 CI 与发布包证据。
- **v0.2——收敛可选能力与分层**：明确阅读器、加密发布和消息投递的依赖边界，区分核心与可选能力的验收成熟度，修正可选依赖文档与实际行为。
- **Later——可维护性**：按领域整理测试命名，清理失效的 phase/wave/docs/plans 引用，合并重复状态锁，拆分超长入口函数。

每条路线应有预期结果和完成判据，而不是只写“优化”“完善”“重构”。GitHub Issues 可跟踪具体执行项，但建议保持 `ROADMAP.md` 为可移植的方向事实源，避免两份路线图漂移。

### 6.5 是否应放在远端仓库

建议 `IDEA.md` 和 `ROADMAP.md` 都公开并纳入版本控制，因为：

- 贡献者需要理解项目目的和明确的非目标；
- 公共路线图有助于解释功能优先级和首版取舍；
- 文档变更可以随代码一起审阅与追溯；
- 这些内容都是通用设计，不含私人语料、真实部署、接收方或凭据。

需要留在私人实例的是具体部署计划、私人内容、真实来源配置、接收方和发布目标，而不是公开产品路线图本身。

简化后的定位是：**`IDEA.md` 管不随版本轻易改变的方向，`ROADMAP.md` 管下一阶段如何接近这个方向，README 管现在实际已经能用什么。**

## 7. 建议的处理顺序

### P0：先完成最初验收，不继续扩大功能范围

以 `IDEA.md:131-142` 为首版清单，补齐三个关键缺口：

3. 对最终 Git 导出包执行干净安装、完整测试和全新实例完整冒烟，并绑定精确提交与 CI。

这一步不需要增加新架构。

### P1：明确首版中可选能力的成熟度

- 保留代码，但清楚标为可选、真实环境尚未验收；

### P2：发布后再处理可维护性

- 合并重复状态锁；
